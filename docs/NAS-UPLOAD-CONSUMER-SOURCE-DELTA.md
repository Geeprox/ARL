# Private Runtime upload consumer source candidate

This candidate is isolated and not adopted. Baseline is ARL checkpoint
`c699bb580e00027bd1fe4ee0174b85d61d986317`, tree
`482428cedec9aa71270efd1eec09ee27ce2491cc`, 550 protected source entries.

The five upload core modules are byte-identical to independently reviewed
upload8 core manifest
`1607601badd1c0ba8ec1d910181492128f233972b56b317b5f159de2befc82fb`.
Their limited core GO does not authorize this new integration or real NAS write.

The integration adds `arl/nas_upload_consumer.py`, extends the existing
`RegisteredPeerVerifier` with an in-process exact-registration lease and adds an
explicit opt-in completion protocol in existing Tool, Runtime and Store. There is
no new engine, queue, journal home, listener, native transport, vendor provider,
credential resolver, source-path decoder or enrollment API. Default Runtime
tools and policies, NAS settings/read-session wire, Portal and logs.v3 stay
unchanged. There is no default write consumer.

The conditional `nas.upload_new.v1` Tool uses the existing Runtime `extra_tools`
and `admission` composition points. A separately reviewed host would have to
explicitly install it, grant it in an `AppPolicy` and supply all private loans.
Its generic submit metadata is only the exact operation UUID and plan hash.
Paths, target, permit, subject, policy epoch, native budget, FDs, credentials and
approval flags cannot be supplied through that schema. No launcher, installation
or current host composition activates it in this increment. The prospective
tool/admission boundary is included in the integration review scope; this
candidate alone grants no RPC write capability.

`RegistrationLease` captures the existing registry record and generation,
revalidates current process identity, and fails after revoke or re-registering
the same PID. It is an executable/birth/registration guard, not a code-signing,
native consent or write-policy grant. The resource owner's separate
`verify_write` must renew those exact native checks and return normally; True
is rejected. Read-session `CredentialBroker` admission is not reused for write.

The consumer pins its exact Runtime, AppPolicy, Store, Tool, admission hook,
registration and resource objects. Both admission and each core owner/effect
guard recheck these pins and the actual `JobContext`. The durable job must be
the verified, first claimed, non-idempotent job for that operation, exact
arguments and tool contract. Another key cannot re-execute its private plan.

The existing Store handles persistent logical call budget, duplicate admission,
queue state, cancellation and recovery. The new completion mechanism is
opt-in; all other tools retain their existing completion semantics. Runtime shutdown, Store cancellation,
JobContext deadline, policy/peer revocation, resource replacement and credential
binding changes fence later effects and positive results. An uncertain or
interrupted non-idempotent upload goes to existing `needs_review`; no automatic
replay, resume, reset or reservation release is added.

Trusted `JournalPolicy` supplies subject and policy epoch plus a logical native
effect budget of 1...16. It is separate from Runtime max_calls and core
MAX_WRITES=128. The existing five-argument native consume seam is invoked once
as `(operation_id, permit_id, subject, policy_epoch, logical_budget)` before
medium effects. Budget denial is finite and cannot become an I/O retry. The
consumer duplicates sealed source/journal FDs, validates the loans, closes only
its duplicates and leaves the resource owner responsible for their lifetime.

R2 fixes the independently reproduced post-return completion gap UC1.
The upload Tool selects completion_fence, which is marked in its contract digest.
Legacy Tool digests are byte-identical when the optional hook is absent.
Runtime captures the handler-return observation time, encodes/bounds the result
and calls Store.finish_fenced. Store freezes that effect observation, then uses
its existing RLock and BEGIN IMMEDIATE transaction for the completion decision
and durable terminal publication. The durable cancel flag and persisted
deadline are read before and renewed after the bounded completion-authority
check. A cancel transaction that wins first produces needs_review; one waiting
for this publication transaction linearizes after completion. No schema
migration, second queue, new journal home or generic finish change is added.

A held completion preserves the fully verified committed effect in a nested
effect record and has top-level status=needs_review plus a finite completion
reason. Actual generated bytes and the core committed receipt remain unchanged;
there is no rollback, second consumption/commit, resume or recovery replay.
The completion record retains the actual audit cancel_requested timestamp and
its order relative to consumer return/publication decision. effect_observed_at
is the handler-return observation time, not an invented native/NAS commit time.
A later cancel on an already completed fenced job gets a separate audit event,
without changing the authorized completion fact. Legacy terminal cancel
behavior is unchanged. Authority and deadline are evaluated at the explicit
transaction decision point; continuous native/remote authority and host
revocation/resource coordination remain held for live qualification.

New bounded checks execute actual candidate Runtime.dispatch/work, Store,
JobContext and registered-peer logic against generated local POSIX bytes. They
do not call Runtime.run, bind/listen, establish IPC, use real peer observations,
read credentials or invoke any native code. `process_identity`, write admission
and the five-argument native consume operation are explicitly synthetic. The
unchanged controlled medium is test-only, not shipped as a NAS adapter. The old
40-test core suite and native suites are not rerun; their exact prior core pins
remain separately bound. R1 CHECKS-3 remains historical evidence. R2 rechecks the affected 18 integration
cases and adds 11 completion tests (including two legacy subcases), with actual
module origins and before/after candidate hashes. The same original reviewer
post-return Runtime.encode cancellation cut must first reproduce r1 negative
(succeeded with cancel=1), then prove r2 held (needs_review with committed
effect retained). Deadline, peer/policy/credential revocation, Store-input
encoding, cancellation waiting on the publication transaction, clean success
and stale completion are included. No old core40 or native suite is rerun.

The following remain held for independent review and later qualification:

- Verified native ConsumptionJournal FD loan/duplicate/seal lifetime and actual
  Python/native five-argument consume bridge; the Swift journal is unchanged.
- Actual native write consent, code/profile/peer policy, subject/epoch/budget
  source, registration and credential lifetime under a concrete host. The
  existing Runtime controls are exercised; synthetic callbacks are not proof
  that this native write admission exists.
- Fresh reconcile read authority and consumer. This increment exposes upload
  only; it does not reuse the upload context as reconcile authority.
- Vendor metadata/query/close timeout, cancellation and late-effect fencing,
  pinned SMB/SFTP API, stable namespace/alias confinement and actual atomic
  durable no-replace semantics. No vendor code is imported or installed.
- Real owner worker/IPC/resource lifecycle and native GUI. No native slot is
  granted. This private Tool must receive exact independent source GO before
  any original adoption; source GO would still not imply live qualification.

The projects do not require contacts. No Contacts/AddressBook usage purpose,
entitlement, framework or API is introduced here. A separate static receipt
checks the current protected ARL baseline only, without reading system contacts
or TCC state. It does not prove OCR/contactsd isolation.

Service deployment, host execution, executor3 and SC1-01 remain deferred.
