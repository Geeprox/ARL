## 修复前事实

此前正式 snapshot 返回系统权限未申请、旧记录暂停。逐字段核对，旧 unknown 回执的 bundle ID、稳定签名要求、政策、来源元数据和绑定证据哈希均匹配；只有可执行文件哈希因代码升级而不同。原回执、来源绑定及元数据在升级/只读验收前后字节未变。

`RemindersUpgradeReview.validate` 将历史回执的完整代码身份与当前身份作相等比较，`receipt()` 因此失败。`snapshot()` 把此失败统一显示为“证据变化”；正常退出旧进程不会改变持久回执，所以不能解决此问题。当前错误并非旧服务仍占用，也不是已证实的来源或预算被改写。

## 最小改动

把稳定主体与代码版本分开使用：稳定主体由固定 bundle ID、稳定签名要求和不变政策确定；当前代码版本继续由封存的 executable/closure 哈希核验。

1. 历史回执及来源绑定通过兼容读取验证稳定主体、政策、run ID、原证据、原来源范围和原到期时间。旧代码哈希保留为历史事实，不覆盖旧文件。仅代码换代不得被误报为证据变化，也不延长来源有效期。
2. 当前 helper、控制端、socket 对端和业务请求仍必须通过本代签名、完整资源封存和代码 pin；不能用稳定主体比较替代实时调用身份检查。既有正常安装器仅更新代码绑定，不新增授权范围。
3. 保留原 disposition 与预算。unknown 仍为 unknown，继续禁止新测试保存；completed 继续消耗原两次上限。不得清空 admission、重建旧回执、换 run ID 或重新取得默认来源来恢复额度。
4. 系统权限与业务门禁分开显示。未申请时提供“允许访问”，仅请求系统提醒事项读写权限，交由用户在系统提示中决定；来源和保存仍由原门禁控制。已授权且 unknown 时显示“结果待核、暂停保存”，不展示保存按钮。

如兼容读取不能证明同一稳定主体、政策或证据，保留原件并暂停。若需要显式版本迁移，只能新增绑定旧原件摘要的旁路记录，不能改写旧证据；迁移记录本身也不能授予权限、续期或恢复额度。

## 当前可用入口与最少操作

当前正式提醒页只有只读“检查连接/重新检查”和停用范围等入口。`upgrade_blocked` / unknown 状态不会出现“允许访问”；“核对旧版”流程也先验证既有回执，不能重签失配回执。通用权限页明确不接管这个专用入口。当前没有一组用户点击可以安全完成重新绑定；不能指导用户删除记录后重试，亦不能用通用 RPC 或终端代替授权主体。

方案实现、审查、正式更新后，同一主体的普通代码升级无需用户重复重绑。系统尚未授权时，用户只需在提醒页点击“允许访问”，再在系统提示中自行决定。此权限由正式提醒服务申请，系统范围为提醒事项读取及写入；不会因此解除 unknown 保存暂停。来源过期时仍须按原流程重新确认原范围。

日历是另一主体和权限：正式 ARL 本体的“服务连接 → 权限 → 创建日程 → 允许创建”请求仅写入日历事件，不读取日程、不建立远端执行授权。本轮自动审批拒绝发起该请求，系统提示尚未出现；需要用户明确授权此具体请求后才能重试。
