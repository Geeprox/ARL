# Taobao R04–R07 robustness source delta

This is a source-only successor to the reviewed cumulative 20-path candidate
`fe250bcb188e052698d18a88f831b1a8f93e864b`. It implements the four requested
robustness changes. No native, official provider, account, cart or transaction
call was run, and no consumer, main repository, permission or installed service
was changed. Prior native receipts qualify only their original source bytes.

The runtime admits only the locally implemented public search and known Tmall
ID/URL/title workflows after the official identity probe. Discovery retains
contracts for consumed names and ignores unrelated directory growth, descriptions
and unused optional schema fields. Compatibility checks the actual sourceApp,
URL, fixed CSS scope, maxLength and offset inputs. Unknown required inputs,
unsupported consumed constraints, conflicting duplicate consumed names and
destructive/read-only behavior changes close only dependent capabilities.
The actual call validates its actual arguments again, so a sample catalog
qualification does not silently admit narrower unknown request behavior.
Status remains a protocol query and exposes finite per-action compatibility
reasons. The general provider tools are never published as user tools.

Official download bundle identity, Apple signing validity, team VJGTV94XY8,
strict static code validity, same UID and PID-owned IPv4 listener remain.
The externally installed app's entire Info/executable hashes and exact 3.0.0
version are no longer universal admission gates. Version/build are diagnostic
metadata; the reviewed 3.0.0 public-page profile is guarded by consumed contracts
and actual response/page checks on later builds. This is not evidence that a
later real supplier build was observed or tested. App Store/other distributions
remain unqualified; no publisher, endpoint or permission allowlist is widened.
Self-published Node/CLI signature inventories are untouched.

The probe returns PID, process birth seconds/microseconds, opaque listen-socket
identity and the fixed endpoint. These fields are compared internally after
discovery and before/after business reading, including before publishing a
result. They are not logged or returned. A changed generation invalidates that
result; the next explicit read creates a new initialize/discover session.
There is no cached permanent session or automatic operation replay. The legacy
fixture route also rejects all writes; no cart journal can be admitted.

A single monotonic 30-second deadline begins before the app probe. HTTP receives
the remaining budget, capped by its existing four-second per-request limit,
and late replies are rejected. Rendering waits consume that same budget rather
than restarting a small fixed window. Navigation is issued once. Every re-read
keeps the same locally fixed public scope, page URL and product identity.
The repeated text guards now share one UTF-16 profile: actual bounded text,
explicit offset zero, remaining zero and a strict false truncation Boolean.
Total length may be absent once those explicit completeness markers are present;
if supplied it must still agree. Unknown declared length units, missing positive
completeness evidence, actual truncation and identity drift remain failures.
No unverified selector or code-point/byte-length profile was added.

`TaobaoRobustnessTests.swift` prepares exactly four decisive production-source
fixture scenarios: additive catalog/per-operation incompatible input, trusted
probe upgrade with publisher/endpoint/write rejection, same-PID generation
change and explicit next read, and slow same-product rendering with metadata,
truncation/identity/late-reply rejection. These Swift regressions are NOT RUN.
The four Python checks only validate fixture integrity against the captured
official catalog/product; they do not prove the new Swift implementation.
No old 37/77/155 suite or transport matrix is scheduled for this delta.

Only four existing production Swift files change; no new production module,
recipe registration or Mio consumer replacement is required. A future minimal
native slot should compile those files with the current owner/consumer closure,
run the four scenarios once, and typecheck the impacted App panel. The unique
writer must compare its current adopted leaf hashes and updated NetEase consumer
dependencies before composing. Formal paired build/install and actual App/Mio
acceptance remain separate steps after review and authorized validation.
