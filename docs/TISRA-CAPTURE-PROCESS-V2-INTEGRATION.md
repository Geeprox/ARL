# Native capture process v2 adoption

This additive source delta completes the three concrete adapters left open by capture runtime v1: kernel-authenticated native communication, observed executable/selected-library pins, and bounded immutable source uploads. It composes the existing ARL Handler, Store, worker, RegisteredPeerVerifier, capture runtime and actual Tisra Core Ledger/receipt journal. Installed host defaults remain disabled. Root owns adoption and activation.

## Source adoption

Apply `capture-process-arl-v2.patch` after ARL v1 commit `42c4a62e0a9a5791a546eaffe69d3bad0cf7087e`; apply `capture-process-tisra-v2.patch` after Core v1 commit `d22b659ac983a2b3babcdb5a85f362b014ea0ec5`. The manifest pins every delivered source file and base hash. Apply with `git apply --check` against the current consumer before adopting; the original Tisra repository remains active WIP and may need a reviewed merge. The separate fixture patch changes only the isolated review harness. Do not add its executable product or stdin registration controller to the installed app.

The sole shared ARL source change imports capture method names from `tisra_capture_uploads`; `Runtime(capture=None)` still exposes no capture route. New Python modules are `tisra_capture_process`, `tisra_capture_uploads` and `tisra_capture_composition`. New Core files are `LinkCaptureProcessChannel`, `LinkCaptureProcessIdentity` and `LinkCaptureProcessJSON`; the small C process observation helper joins the existing TisraCloudHost target. No UI, Ledger schema, research history, frozen inner v1, installed host or generic scheduler file is changed by this delta.

## Trusted host construction

1. Select an explicit Ledger and existing `LinkCaptureReceiptJournal`, with matching library UUID and restore-instance UUID. These values and exact executable SHA256 come from host-owned observation and registration, never source RPC or declared writer fields. The native channel additionally pins the selected `ledger.sqlite` device/inode; replacing that file fails closed.
2. In the native owner process, observe `LinkCaptureProcessIdentity.observe(pid:)` for itself and the actual ARL host. Create `LinkCaptureProcessRegistration` values for separately observed source processes, binding app, authenticated participant, actor kind, opaque authorization epoch, library and current write grant. Supply a live host-owned registration closure to `LinkCaptureProcessChannel.Configuration(ledger:journal:host:native:registrations:)`. An empty/default `LinkCaptureProcessChannel()` has no endpoint. Start an explicitly selected socket in a private owned directory and accept through `serveNextConnection()`; call `stop()` at shutdown.
3. On ARL's trusted host side, reuse one `RegisteredPeerVerifier` with the explicitly approved app identifiers. Separately register the native process through its existing `register(app,pid,expected_executable)` API. Use `CaptureProcessRegistrations(verifier)` and `register(app,actual_source_pid,expected_executable,expected_sha256,participant)` for source participants. Failed image verification enrolls nothing. Both registrations remain volatile process observations; there is no enrollment RPC.
4. Construct `CaptureConsumerPin(library_id,instance_id,actual_native_image_sha256)` and `CaptureProcessComposition(verifier,registrations,native_app,native_pid,expected_executable,expected_sha256,socket_path,selected_ledger,pin,participants,library_grants,method_grants,active=False)`. `selected_ledger` is the exact SQLite file, not its directory. Grant only the required capture/upload method names in both explicit AppPolicy and method grants. Set `active=True` only through the authorized host configuration after acceptance. `make_runtime(home,policies=...)` retains the existing Runtime and disables model execution. Stop Runtime before `composition.close()`.
5. A restarted native PID requires a separately observed verifier registration, then host-only `replace_native_consumer(new_pid)`. It preserves selected path/library/restore/code/schema pins, closes the old retained file descriptor and never replays a task. Changing code, restore instance or selected library requires a new explicit composition and acceptance.

Native grants independently match the bound source process and principal before and after each callback. The bidirectional authorization event is bound to the exact capture ID, full request hash/count, stage and record index on the authenticated socket. Each event uses a fresh UUID. ARL rechecks current policy, grants, registration generation, image, epoch, native pin and cancellation. A returned boolean cannot create native authority. Declared source/contribution writers remain untrusted provenance and can differ from the authenticated caller.

## Source calls and bounds

Reuse `Client.rpc` on the existing `arl/1` channel. Source declares only `capture.upload.begin.v2 {capture_request_id,library_id,sha256,byte_count}`, then contiguous `capture.upload.append.v2 {payload_id,offset,data_base64}`, then `capture.upload.seal.v2 {payload_id}`. The host allocates payload IDs and returns the immutable v1 payload reference `{payload_id,sha256,byte_count}`. Submit that reference through the unchanged `capture.submit.v1`; poll status, read the confirmed result in bounded chunks and compare the full SHA256/count. No source-selected path, owner, epoch, purpose, authority or consumer is accepted.

Complete request/result/outer byte caps remain 524288/32768/8192. Frames are capped at 16384 complete bytes including LF; decoded chunks are 1..8192. Excess is rejected, never truncated. Upload defaults: TTL 900 seconds; owner/global declared-byte budgets 2097152/16777216; owner/global active upload counts 8/128; 4096 total metadata records. Reservations include all declared bytes, and sealed data has SQLite immutability triggers. Revocation, cancellation or expiry removes bytes irreversibly. Restart invalidates unsealed uploads; sealed uploads remain exact until expiry/revocation. Expired input cannot authorize receipt publication, while the native durable journal keeps its committed outcome.

Native permits eight concurrent sessions, at most one request and one result upload per session, and 256 retained initial Core results. Python uses a fresh authenticated connection per operation and an absolute 15-second deadline (configurable up to 60 seconds), at most 64 authorization events and 64 observed commits/8 MiB of observed requests. Separate metadata sessions avoid a callback/guard deadlock. Capacity and uncertain outcomes hold or reject; they never select a fallback provider.

`capture.status.v1` in the v2 subclass holds the configuration lock across the entire state/receipt snapshot. A terminal success always carries the receipt from that same observation. Peer source deduplication preserves the first stored writer, validated against real stored provenance rather than the retry writer.

## Durable outcomes and acceptance

The actual native Ledger and separate receipt journal remain distinct transactions. ARL durably holds an uncertain delivery before sending the safety-only native hold notice; these two commits are not atomic. Losing that notice cannot erase the ARL hold. Fresh authorization and live native reference validation are required for confirmation, ACK and each result chunk. Only an acknowledged exact journal result is recoverable as success; unacknowledged or unknown effects require review and never auto-replay. A held capture ID blocks a fresh upload.

The finite end-to-end test launches an isolated Swift consumer and genuine separate source process, registers only test identities, and writes only disposable synthetic Ledger/journal stores. It proves upload -> actual Core save -> confirm -> ACK -> exact result bytes; independent native revocation; unregistered source rejection; upload excess/rebinding/revocation rejection; peer retry retaining the first writer; acknowledged native restart preserving receipt bytes; and a lost ACK followed by both native and ARL restart retaining `needs_review` without new records. Process unit tests additionally reject wrong executable, PID generation, schema, restore-instance and selected Ledger inode. See the manifest's pinned logs and receipt files.

All source paths are implemented. Remaining live work is root-owned integration into the chosen installed host, explicit real app/principal/library/method grants and restore-instance lifecycle, and a separately authorized live acceptance/activation. No production registration, private library, credential, signing key, model inference or deployment was used. The held Friday component remains untouched.
