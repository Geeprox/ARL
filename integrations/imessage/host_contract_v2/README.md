# Native Messages contract v2 — isolated source candidate

This answers the two Messages contract questions in FutureControl `0eff41b12e4f8b42e0a28b4b4951aaedef3046c4`, `docs/OCT3-FUTURE-INTEGRATION.md`. All task-11 `1628ea94` source/artifact bytes and shared FutureControl bytes stay unchanged. Import and activation are separate root decisions; default admission remains nil. No clock trigger, deployed service, OS grant, personal database access, live group send, private key, new tunnel/plugin/key, or Mio event claim is created here.

## Existing code reused

The fixed native launch was already implemented in `control_future/Sources/MessagesProductClient.swift`: only explicit Begin can launch the reviewed bundle with `--serve`; snapshot cannot launch. The gap was the store requiring a snapshot before enabling that same Begin. There is no added generic bootstrap RPC, helper registry or arbitrary script surface. The v2 client keeps the existing fixed launch and adds a read-only candidate inspection; its result means only **identity/closure/policy verified, running status unknown**. Explicit Begin can then try that one fixed launch without a first snapshot. Once connected, backend-ready evidence comes from the actual owned Python initialize response with its identity echo verified. Account, OS permission, group and trial evidence stay separate.

The existing Python backend initialization constructs `MessagesDatabase` without opening it (`arl_imessage/database.py` constructor). It initializes the private controller journal, not a Messages SQL snapshot or permission request. Retest, metadata discovery and receive/send remain separate bounded actions. Existing `OnboardingController._ui` and its durable journal already suppress repeated command UUIDs; native send consumption already occurs before dispatch. V2 retains these mechanisms and serializes only owned backend stop work. Credentials need no new bootstrap: the existing real disabled owner instance is sufficient for the held FutureControl scope.

## New native authority and wire

Control requests have `schema_version: 2` and retain the exact four fields and finite v1 command/argument sets. There is no `bootstrap`, target, path, text-body, grant, script or media command. The native wrapper converts only this finite frame to the unchanged private v1 backend. Replies have outer version 2 and a required `authority` on every success; core snapshot/presentation/plan retain their existing version/shape. Errors carry no success claim. V1 frames/replies fail closed; there is no authority fallback from a generic counter.

`Shared/MessagesAuthorityV2.swift` defines the exact Codable authority structure and strict field sets:

| Field | Source and meaning |
| --- | --- |
| `run_id`, `policy_sha256` | Exact sealed native run and policy, matched to root's immutable admission |
| `host_generation`, `revision` | Durable monotonically increasing boot/revision values; UI rejects rollback or changed evidence at the same revision |
| `started_at`, `deadline`, `observed_at`, `expired` | Original native deadline and durable clock high-water; expiry is sticky |
| `backend_ready` | Actual sealed owned-pipe initialization and identity echo passed; never OS or transport readiness |
| `send.limit`, `consumed`, `outcome`, `operation_id` | One lifetime attempt; `unused`, `consumed_unknown`, or `accepted`. Accepted means command acceptance, not delivery |
| `lease.state`, `session_id`, `generation`, `scope_id` | Actual native lease binding: inactive, active, revoked or expired |
| `cleanup.epoch`, `state`, `session_id`, `generation`, `operation_id` | Durable operation-bound cleanup transition. In-progress/unknown blocks reconnect; completed requires exact captured operation/epoch, actual scoped stop proof and no occupied permission request |

One private `run-v2.json` **replaces** v1's native `ceiling.json` and `scope.json` in this new composition. Its internal record format is now **3**, separate from public wire version 2. It includes the same typed scope, one consumed flag/outcome, original deadline, boot/revision, cleanup operation/epoch, durable cleanup-request history and clock high-water. No redundant native send journal is added alongside the v1 files. The Python journal still owns controller requests/cursors/content cleanup; it does not become native authority. V2 refuses a root containing v1/partial controller state when the new record is absent. The independently rejected v2 record format cannot establish historical idempotency and is also refused with its bytes preserved. There is no automatic migration, deletion, journal reset or budget regeneration. Original host locking/private-directory rules remain in the new server composition.

The version-2 sealed policy adds `run_not_after`, and the signed bundle must declare `ARLMessagesWireVersion = 2`. The original absolute deadline is persisted once as `min(first native start + 900s, sealed run_not_after)`. Root's `MessagesProductAdmission.notAfter` must equal that sealed value and remains immutable across every reconnect/restart. This seals the previously UI-only conservative bound into the actual host. A disabled policy may use zero; an enabled candidate requires a concrete positive value. Root must create/review new exact Control/helper/policy/closure pins; the frozen v1 candidate cannot satisfy v2 checks. Policy/identity changes do not silently retag existing journal authority.

Consumption is fsynced before the native callback acknowledges permission to dispatch. Uncertain writes make the journal unusable; persisted unknown consumption remains spent after restart. Outcome, operation, lease/group/participant pin and revocation cannot be reset by replay. The first activated group's pin remains fixed for this run even after unused-lease cleanup. Restart revokes any old lease and records unknown cleanup for an unclosed boot, preserves deadline/consumption and never resumes a send. A correctly completed shutdown preserves clean evidence, still under the original deadline and send budget.

Cancel/disable persist a UUID/command fingerprint and native cleanup token (operation UUID, epoch, host generation, session/generation and lease binding) atomically with lease revocation before backend stop dispatch. All previously admitted UUIDs remain idempotent across intervening requests and restart; replay returns the original token with no new epoch, binding change or stop dispatch. Conflicting command reuse is rejected. History is bounded at 64 requests, never evicted; exhaustion makes authority fail closed. Core snapshots cannot complete any cleanup, including a matching current session. The native caller retains its token across the exact owned-pipe `lifecycle_stop` request and checks that correlated reply's actual `CleanupProof`: grant, receiver, publisher and children stopped plus private content cleaned. Conditional completion must still match the current token/epoch/host generation and unoccupied native permission call. Older same-session proofs also fail. Owned stops are serialized, so a prior stop cannot continue cleaning private content after newer cleanup completion permits a lease. Native lifecycle shutdown additionally awaits owned backend termination before conditional completion; shutdown alone cannot upgrade unknown/pending cleanup. After native expiry, a restarted server can exist for at most 45 seconds for status/owned cleanup only; the original deadline stays expired and all setup/effect checks still refuse it. Passive UI status never launches that server; a disconnected post-expiry cleanup result remains unknown and requires root coordination.

V2 snapshot projection advances only the native private journal's clock high-water/sticky expiry. It does not call OS permissions, inspect Messages, discover groups, renew a grant or dispatch an effect. This is a native metadata write; the existing backend's core snapshot is still pure. Durable clock tracking prevents rollback/restart from extending the run, and any interrupted native write fails closed.
