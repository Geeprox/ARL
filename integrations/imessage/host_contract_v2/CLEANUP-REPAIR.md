## Reproduction and corrected invariants

The exact independent `MessagesV2CleanupProbe.swift` was compiled against the original local source and reproduced both defects in synthetic journals. `evidence/host-contract-v2-cleanup-before.json` records stale S1 completion releasing S2 cleanup and allowing an unused S3 lease, same-session old completion finishing a newer epoch, and A→B→replay A advancing epoch 2→3. No live timing race or helper was exercised.

`MessagesRunJournalV2.reconcile` now treats every core snapshot as presentation only. Completion uses a captured `MessagesCleanupOperationV2`, not the journal's current token stamped onto a response. It compares the entire persisted operation, current epoch and host generation and checks exact session/generation, retained lease binding, native grant revocation, permission occupancy and all actual stop-proof fields. Stale, unknown, incomplete or malformed proof cannot upgrade cleanup. A new lease is blocked by uncertain cleanup even when no earlier lease existed.

Before dispatch, `beginCleanup` atomically persists the request UUID, canonical finite-command fingerprint, operation UUID, epoch, host generation and scope binding with revocation. A→B→replay A returns A's original token; the current B token is unchanged. Native host replay takes only a pure owned-backend snapshot and never redispatches the earlier cancel/disable. History survives restart and uncertain writes. No entries are evicted; after 64 distinct requests, new requests fail closed. Reusing a UUID for the other command is rejected without mutation. The Python controller's original idempotency remains intact but is not relied upon to suppress native admission.

## Actual proof routing

The existing sealed backend and adapter source remain unchanged. For a fresh cancellation, the native host captures its admitted operation before queueing work, dispatches the finite cancel/disable, and then requests the existing private `lifecycle_stop` operation. That operation cancels/waits for its worker, calls the adapter's actual scoped stop and returns `CleanupProof`; a core `cleanup="completed"` snapshot is never used as proof. `MessagesBackendPipe` correlates the reply to its unique owned request continuation. The native closure retains the operation admitted **before** that request across the await and passes that exact captured token with the returned proof into conditional completion. There is no lookup that substitutes a newer current token for an older reply.

`MessagesCleanupQueueV2` serializes these stops, including native lifecycle stop, because an earlier stop must exit before a newer stop can establish completion. Native `stop_trial` callbacks only revoke/preserve the current binding; they cannot rebind or complete an in-flight operation. A superseded request may not dispatch its stop, and a delayed already-dispatched stop cannot complete a newer epoch. Occupied native permission calls hold cleanup until they exit. Cleanup admission is persisted before any backend await, using the active lease or cached pure setup-session status. Startup obtains that pure status without OS/SQL access. A stale or unavailable binding remains uncertain and is never filled from a later completion; an explicit fresh cancel can use subsequently refreshed status. Lifecycle shutdown additionally requires owned backend reap; failed startup/session lookup cannot preserve a prior completed proof, and `shutdown()` alone never claims successful cleanup.
